# 网络代码框架化重构计划

> **制定日期**: 2026-08-22
> **执行者**: main_network（程序实现）+ main_qa（每里程碑回归）
> **前置阅读**: `TechnicalDocs/状态同步实施计划.md`（M1-M4 已实现内容）、`TechnicalDocs/Client/客户端流程审查报告_2026-08-22.md`（问题编号 I/J/X 引用自该报告）

**Goal:** 将 `Client/Assets/Scripts/Network/` 按"框架层 / 业务层"彻底分离：通用网络框架（连接、收发、心跳、分发、限频）落入 `Framework/Network/`（随 `DualEnigma.Framework.asmdef` 程序集，零业务依赖，可跨项目复用）；业务代码按 `Protocol / Session / Sync / Rest` 归位；消灭 `GameServerClient` 大杂烩与 `NetworkSystem` 死桩。**全程协议字节不变、服务器零改动**，并顺带修复审查报告中的 I（状态残留）、J（进房无反馈·客户端侧）、X（误导桩方法）三个问题。**R5 里程碑交付完整请求-响应体系**（连接层本地枚举 + 业务层 `reqId`/`S2C_Resp` 统一回执），保证**每一个 C2S 请求都有明确的响应码**（0=成功，非 0=失败原因，本地 -1=无响应超时），杜绝"石沉大海"。

**Architecture:** 分层架构，依赖方向严格单向：`Framework/Network`（只依赖 Framework.Core）← `Scripts/Network/Protocol` ← `Scripts/Network/Session` ← `Scripts/Network/Sync|Rest` ← 各业务系统。会话状态收敛到 `RoomSession` 单一事实来源；消息路由用注册表替换巨型 switch。

**Tech Stack:** Unity 2022.3 C#（System.Net.WebSockets / JsonUtility 既有选型不变）· Spring Boot game-server（本计划零改动）

## 〇、四条铁律（执行时时刻对照）

1. **协议字节不变**：重构前后 WebSocket 上跑的 JSON 一字不差。所有 DTO 字段名/嵌套结构原样搬运，只改 C# 可见性。
2. **服务器零改动（R1–R4）**：R1–R4 严禁修改 `Server/`；**R5 是唯一例外**，仅新增 `S2C_Resp` 统一回执消息、C2S 请求的 `reqId` 字段及各处理路径的回执调用（不改动任何既有消息结构、不改既有消息的收发时机）。其余服务器需求（重发策略、重连快照、协议版本号）仍归后续计划。
3. **每里程碑独立可验收**：编译 0 error + 双开回归通过即可提交，随时可停。每个里程碑一个 git 分支（`refactor/net-r1` ...），失败整分支回滚。
4. **行为不变原则的两个例外**（都是修 bug，需在 R3 验收时专项确认）：
   - 主动退出对局后 `NetworkSystem` 状态不再残留（审查报告 I）；
   - 进房 5 秒无 `S2C_ConnectAck` 时客户端本地超时提示（审查报告 J 的客户端兜底）。

### Task 5.1：协议定义（双端）

所有 C2S 请求新增公共字段 `reqId`（客户端每连接自增序号，从 1 开始；服务端只回显、不解释其含义）。新增统一回执消息：

```json
// 上行：所有控制类请求带 reqId
{ "type": "C2S_StartGame", "reqId": 7, "data": {} }

// 回执：每个 reqId 必须且仅有一条，只发给请求者本人
{ "type": "S2C_Resp", "timestamp": 1761234567890,
  "data": { "reqId": 7, "code": 0, "message": "ok" } }
```

**错误码表（双端单一事实来源，逐项对照实现）**：

| 码值 | 含义 |
|------|------|
| **0** | 成功 |
| **-1** | 回执超时（**客户端本地判定，不下发**） |
| 1001 | Token 校验失败（预留，是否启用取决于账号服鉴权策略，实施前核对 ConnectHandler 现行行为） |
| 1002 | 未支持的消息类型 |
| 2001 / 2002 / 2003 | 房间不存在 / 房间已满 / 对局已开始 |
| 3001 / 3002 / 3003 | 非房主 / 未满员 / 对局已在进行 |
| 4002 | 碎片上报被拒（上报者不在判定半径） |

**回执覆盖矩阵（每个请求 → 谁回什么）**：

| C2S 请求 | 成功回执 | 失败回执 | 领域消息（照旧不变） |
|----------|---------|---------|---------------------|
| `C2S_Connect` | resp(0)（紧邻 ConnectAck 前发） | 2001/2002/2003，**回执后关闭该会话** | `S2C_ConnectAck` + `S2C_PlayerJoined` |
| `C2S_StartGame` | resp(0)（发请求者） | 3001/3002/3003 | `S2C_GameStart` 双方广播 |
| `C2S_FragmentCaught` | resp(0)；**过期/重复上报同样回 0**（幂等静默，避免竞态噪音） | 4002 | `S2C_FragmentResult` 广播 |
| `C2S_HighFreqState` | ⚠️ 见下方"豁免决策" | — | `S2C_HighFreqState` 转发给对方 |
| `C2S_Heartbeat` | 豁免：`S2C_HeartbeatAck` 即其专属回执（RTT 语义专用，不改） | — | — |

> **豁免决策（执行 R5 前需项目拍板）**：`C2S_HighFreqState` 为 20Hz 单向流，逐条回执将使每客户端消息量翻倍（+20 条/s ≈ 1.2KB/s）且无任何消费场景——TCP 已保证送达、失败也无处理分支；Mirror/NGO/Photon 均不对高频位置流逐条 ack。**推荐豁免**（上表默认按豁免设计）。若坚持全量覆盖：服务器对 HighFreq 逐条回 resp(0)，代价如上，客户端不登记其 reqId（仅服务器侧满足"全请求有回执"）。

```csharp
/// <summary>轻量请求跟踪器：登记 reqId → 超时扫描 → 回执派发。</summary>
public class RequestTracker
{
    /// <summary>发送前登记。onResp 必被调用一次（成功回执 code / 本地超时 -1）。</summary>
    public int Register(string sourceType, float timeoutSec, Action<int, string> onResp);
    public void OnResp(int reqId, int code, string message);   // 收到 S2C_Resp 派发
    public void Tick(float deltaTime);                          // 超时扫描（code=-1 回调）
}
```

处理规则：
1. `resp.code != 0` → 若为 Connect 请求先取消进房看门狗（防双提示）→ 发布 `NetworkErrorEvent` → `source == C2S_Connect` 自动 `Disconnect()`（回主界面初始按钮态）；
2. 回执超时（code=-1，本地）→ 提示"操作无响应，请检查网络"；**仅提示不自动断线**，连续超时升级策略归 R6；
