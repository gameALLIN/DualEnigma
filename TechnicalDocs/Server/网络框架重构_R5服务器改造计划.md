# R5 服务器改造计划 — reqId + S2C_Resp 统一回执

> **制定日期**: 2026-08-22
> **归属**: 《TechnicalDocs/网络框架重构计划.md》里程碑 R5 的服务器侧详细设计（客户端侧设计见该文档 Task 5.1–5.4）
> **执行者**: main_network（实现）+ main_qa（验收）
> **服务器代码基线**: 本次审查已逐文件核对 `Server/network` 与 `Server/game-server` 全部相关源码，行号引用以当前版本为准

**Goal:** 服务器对**每个携带 reqId 的 C2S 请求必须且仅回一条 `S2C_Resp{reqId, code, message}`**（code=0 成功 / 非 0 失败），并修复全部"只打日志不回包"的静默拒绝分支。既有领域消息（ConnectAck/GameStart/FragmentResult 等）的结构与收发时机**零变化**。

**Tech Stack:** Spring Boot 4.1 · Java 21 · Jackson（既有 MessageCodec 多态信封，`@JsonTypeInfo(property="type")`）

---

## 一、现状梳理（基于源码核对）

### 1.1 消息处理链路（当前）

```
WebSocket 文本帧
  → GameWebSocketHandler.handleTextMessage          [network]
      messageCodec.decode(json)                     Jackson 多态 → Message 子类
      heartbeatManager.getClientSession(sessionId)
      messageRouter.route(clientSession, msg)
          → handlers.get(type).handle(session, msg) EnumMap 路由
              ConnectHandler     → RoomManager.onPlayerConnect(session, roomCode)   void
              StartGameHandler   → RoomManager.requestStart(session)                void
              FragmentHandler    → room.onFragmentCaught(...)                       void
              HighFreqHandler    → room.forwardHighFreqState(...)                   转发
              HeartbeatHandler   → 回 S2C_HeartbeatAck                              ✅ 唯一有回执的
              Building/Skill/Synthesize/TalentHandler → room.onXxx(...)            全 TODO
```

### 1.2 静默拒绝点清单（本次要消灭的）

| # | 位置 | 当前行为 | 后果 |
|---|------|---------|------|
| 1 | `RoomManager.onPlayerConnect` 进房三分支（房不存在/已满/已开局） | `log.warn` 后 return，**不回包** | 客户端永久挂起（审查报告 J） |
| 2 | `RoomManager.requestStart` 拒绝分支（非房主/未满员/已在进行） | `log.warn` 后 return，**不回包** | 房主点击无反馈 |
| 3 | `GameManager.onFragmentCaught` 仲裁拒绝（不在半径） | `log.warn` 后 return，**不回包** | 客户端无权威确认 |
| 4 | `GameManager.onFragmentCaught` 过期/重复 | `log.debug` 静默 | 预期竞态，保持静默但需归入回 0 |
| 5 | `MessageRouter.route` 未注册 handler | `log.warn`，**不回包** | 调试期盲区 |
| 6 | `GameWebSocketHandler.handleTextMessage` decode 失败（含未知 type 字符串） | catch 后 `log.error`，**不回包** | 协议错误无反馈 |

### 1.3 关键既有事实（改造时不要重新调查）

1. `Message` 基类（network/protocol/Message.java）只有 `timestamp`/`playerId` 两个信封字段，**无 reqId**；子类经 `@JsonSubTypes` 注册，新增消息必须同步注册 + 加 `MessageType` 枚举值。
2. `MessageCodec` 已配置 `FAIL_ON_UNKNOWN_PROPERTIES=false`（多余字段容忍）——旧客户端不识别 `S2C_Resp` 也不会解码崩溃；客户端 JsonUtility 同样忽略未知字段 → **双端旧版本均向后兼容**。
3. `ClientSession.send()` 已 synchronized（Tick 线程与消息线程并发安全），但**没有 close() 方法**——服务器主动关连接目前无封装。
4. `HeartbeatManager.removeSession` 会通知 DisconnectListener（RoomManager.onDisconnect）；进房失败的会话 `roomCode == null`，onDisconnect 里 `if (roomCode == null) return` 提前退出——**回执后关连接不会误触房间清理**。
5. Handler 注册模式：各 Handler `@PostConstruct` 里 `messageRouter.register(MessageType.X, this)`，构造器注入依赖——新依赖照此注入。
6. `RoomManager` 是 @Component 单例；`GameManager` 每房间一个实例（构造于 GameRoom）。

## 四、Task S2：回执基础设施（network 模块）

### S2.1 `RespSender.java`（唯一回执出口）

```java
package com.dualenigma.network;

/**
 * 统一回执发送器。所有 S2C_Resp 一律经此发出（禁止散落手工构造，保证 timestamp/格式一致）。
 */
@Component
public class RespSender {

    private final MessageCodec messageCodec;

    public RespSender(MessageCodec messageCodec) { this.messageCodec = messageCodec; }

    /** 向指定会话回执。reqId=0（旧客户端未携带）同样回执，客户端旧版会安全忽略。 */
    public void reply(ClientSession session, int reqId, int code, String message) {
        if (session == null || !session.isOpen()) return;
        try {
            S2C_Resp resp = new S2C_Resp();
            resp.setPlayerId(-1);
            resp.setTimestamp(System.currentTimeMillis());
            resp.getData().setReqId(reqId);
            resp.getData().setCode(code);
            resp.getData().setMessage(message != null ? message : "");
            session.send(messageCodec.encode(resp));
        } catch (Exception e) {
            log.warn("Failed to send resp(reqId={}, code={}): {}", reqId, code, e.getMessage());
        }
    }

    /** 便捷重载：NetErrorCode 常量版。 */
    public void reply(ClientSession session, int reqId, int code) {
        reply(session, reqId, code, NetErrorMsg.of(code));
    }
}
```

`NetErrorMsg`：码值→默认中文文案的小工具（可与 RespSender 同文件静态方法），客户端展示用 message 以服务器为准（客户端也有本地兜底文案，见主计划 Task 5.3）。

- [x] S2.1.1 创建 RespSender（含文案映射）。

## 六、Task S4：业务层返回码（game-server 模块，改签名不改逻辑）

### S4.1 `RoomManager.onPlayerConnect` → `int`

| 现分支 | 现代码 | 改后 return |
|--------|--------|------------|
| 指定 roomCode 但房间不存在 | `log.warn(...)` + return | `return ROOM_NOT_FOUND` |
| 房间已满 / 已开局 | 同上 | `return ROOM_FULL` / `return GAME_STARTED` |
| `addPlayerToRoom` 内 room.addPlayer 失败（并发满员） | `log.warn` + return（在私有方法内） | **私有方法也改返回码**，失败上抛 `ROOM_FULL` |
| 成功 | sendConnectAck + broadcastPlayerJoined | `addPlayerToRoom` 内在 `sendConnectAck(...)` **之前**插入 `respSender.reply(session, msg 的 reqId, OK)`；然后 `return OK` |

⚠️ reqId 的传递：`onPlayerConnect(session, roomCode)` 现签名不含 msg。**两个方案二选一**（推荐 A）：
- **A（推荐）**：签名改为 `onPlayerConnect(ClientSession session, String roomCode, int reqId)`，reqId 由 ConnectHandler 传入——显式、可测。
- B：成功回执移到 ConnectHandler（拿到 OK 后先 reply 再由 RoomManager 发 Ack）——但会破坏"resp 紧邻 ConnectAck 前"的顺序保证（两次调用间有广播插入风险）。**不要选 B**。

- [x] S4.1.2 addPlayerToRoom 失败分支返回码上抛。
- [x] S4.1.3 成功路径 resp(0) 插入点：`sendConnectAck` 调用语句的紧前面。

## 七、豁免、预留与未来规则

### 7.1 豁免清单（不回 S2C_Resp，已与主计划 Task 5.1 对齐）

| 请求 | 豁免理由 | 替代回执 |
|------|---------|---------|
| `C2S_Heartbeat` | RTT 语义专用 | `S2C_HeartbeatAck`（现状保留，不改） |
| `C2S_HighFreqState` | 20Hz 单向流，逐条回执消息量翻倍且无消费场景（**主计划 Step 5.1.2 拍板项**，默认豁免） | TCP 送达保证 + 对方收到 `S2C_HighFreqState` 转发即为处理结果 |

### 7.2 预留不发：1001 Token 无效

`ConnectHandler` 现行为：token 校验失败 → 匿名放行（不拒绝进房）。**本计划不改变此策略**，`TOKEN_INVALID` 仅作为码值预留；若未来产品要求"必须登录才能联机"，改造点只有 ConnectHandler 一处（校验失败 → reply(1001) + close）。

### 7.3 未来 Handler 的强制契约（写给后续里程碑）

`BuildingHandler / SkillHandler / SynthesizeHandler / TalentHandler` 目前是 TODO 空壳（room.onXxx → TODO）。**任何后续实现必须遵守**：

1. 业务方法返回 int 码，Handler 层统一 `respSender.reply(session, msg.getReqId(), code)`；
2. 新增码值：建筑/合成段建议 5xxx、技能/天赋段 6xxx，先改双端码表再写逻辑；
3. 长耗时操作（如合成校验）先回 resp(0)（受理）再用领域消息推结果——受理与结果分离。

## 八、兼容性分析（新旧版本互通矩阵）

| 组合 | 行为 |
|------|------|
| 新客户端 + 新服务器 | 完整 reqId/resp 闭环（目标态） |
| **旧客户端 + 新服务器** | 旧客户端不发 reqId → 基类反序列化为 reqId=0 → 服务器照常回 resp(reqId=0)；旧客户端 `DispatchMessage` 的 switch 落 default 分支静默忽略 `S2C_Resp`（已核对现状 default 无副作用）✅ **且顺带修复旧客户端挂死 bug**：进房失败从"永久挂起"变为"收到 resp(无视) + 被服务器关闭 → 触发既有断线提示路径" |
| 新客户端 + 旧服务器 | 新客户端发 reqId，旧服务器 Jackson `FAIL_ON_UNKNOWN_PROPERTIES=false` 忽略未知字段**但基类没有 reqId 字段会被丢弃**，无 resp 返回 → RequestTracker 5s 超时兜底提示"操作无响应" ✅ 降级可用 |
| 旧客户端 + 旧服务器 | 现状不变 |

结论：**服务器可先行部署**（对旧客户端零破坏且有改善），客户端 R5 合入后自动获得完整闭环——部署顺序无强约束。
