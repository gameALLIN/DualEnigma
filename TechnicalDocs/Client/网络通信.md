## 一、系统概述

网络通信负责：
- 客户端与服务端通信
- 消息序列化/反序列化
- 状态同步
- 延迟补偿与冲突处理
- 断线重连状态恢复

### 1.1 项目网络约束

| 约束 | 说明 |
|------|------|
| 联网模式 | 强制双人联网（无单人模式） |
| 平台 | PC（键鼠） |
| 单局时长 | 36关×90秒≈54分钟（长局游戏） |
| 单轮结构 | 7阶段90秒（预告→碎片收集→灾害预告→建造→灾害冲击→修整→升级） |
| 断线处理 | 30秒重连窗口 + AI接管 + 120秒超时（详见§六） |
| 网络协议 | TCP + UDP（可靠+不可靠混合） |
| 序列化 | Protobuf |
| 服务端 | C++ 微服务（⚠️ Host-Client模式下房主兼Host，详见§二） |

## 二、同步架构选型

### 2.1 架构决策：状态同步（State Sync）

**推荐采用状态同步，而非帧同步（Lockstep）。**

| 对比维度 | 状态同步 | 帧同步（Lockstep） | 本项目适配度 |
|----------|----------|---------------------|--------------|
| 操作精度要求 | 适合中等精度 | 适合高精度（格斗/RTS） | ✅ 2D合作游戏精度要求中等 |
| 断线重连 | 直接同步当前状态即可恢复 | 需重放历史帧，恢复复杂 | ✅ 状态同步恢复更简单 |
| 长局累积误差 | 无累积误差 | 帧间误差累积，54分钟长局风险高 | ✅ 状态同步无累积风险 |
| 同步数据量 | 仅同步状态快照 | 需同步所有玩家输入 | ✅ 2人+碎片+建筑，数据量小 |
| 实现复杂度 | 中等 | 高（确定性模拟+回滚） | ✅ 状态同步更可控 |
| 防作弊 | 服务端权威，天然防作弊 | 客户端模拟，需额外防作弊 | ✅ Host权威模式 |

### 2.2 网络拓扑：Host-Client 模式

```
┌─────────────────────────────────────────────────────────┐
│                    Host (房主)                           │
│  ┌─────────────┐    ┌──────────────┐    ┌────────────┐ │
│  │  游戏逻辑    │◄──►│  权威状态     │◄──►│  网络层    │ │
│  │  (本地模拟)  │    │  (Authoritative)│   │  (Host端)  │ │
│  └─────────────┘    └──────────────┘    └──────┬─────┘ │
│                                        TCP+UDP │       │
│                                    ┌────────────┘       │
└────────────────────────────────────┼────────────────────┘
                                     │
                          ┌──────────┼──────────┐
                          │     网络链路          │
                          └──────────┬──────────┘
                                     │
┌────────────────────────────────────┼────────────────────┐
│                                    ┌────────────┐       │
│                        ┌───────────┤  网络层    │       │
│                        │           │  (Client端)│       │
│                        ▼           └────────────┘       │
│  ┌─────────────┐    ┌──────────────┐                     │
│  │  游戏逻辑    │◄──►│  本地状态     │    Client (另一玩家) │
│  │  (本地模拟)  │    │  (预测+插值)  │                     │
│  └─────────────┘    └──────────────┘                     │
└─────────────────────────────────────────────────────────┘
```

**Host-Client 模式说明：**

| 角色 | 身份 | 职责 |
|------|------|------|
| Host | 房主（创建房间的玩家） | 权威状态管理、碎片掉落计划生成、灾难随机种子生成、冲突判定、建筑摧毁判定 |
| Client | 加入房间的玩家 | 本地预测模拟、接收Host同步的状态、发起本地操作事件 |

**Host权威原则：**
- 所有关键事件（碎片接住冲突、建筑摧毁、灾难随机性）由Host判定，Client服从
- 高频状态（角色位置/速度）由各端本地模拟，Host定期校正
- 阶段切换由Host驱动，同步给Client

> ⚠️ **技术栈待定**：Unity Netcode for GameObjects vs Mirror 尚未最终选型。AGENTS.md 标注为 TBD。两者均支持 Host-Client 模式，选型不影响本文档定义的同步规范。待原型验证后确定。

> 🔲 **待讨论**：是否需要独立的中转服务器（Relay Server）用于NAT穿透，还是依赖P2P直连+STUN/TURN。PC平台可考虑Steam Relay。

## 三、网络同步内容分类

### 3.1 同步类型总览

| 同步类型 | 同步内容 | 频率 | 可靠性 | 传输协议 | 优先级 |
|----------|----------|------|--------|----------|--------|
| 高频状态 | 角色位置/速度/动画状态 | 20次/秒（50ms） | 不可靠 | UDP | 高 |
| 中频状态 | 庇护能量值、HP、碎片位置 | 10次/秒（100ms） | 可靠 | UDP（可靠通道） | 中 |
| 关键事件 | 碎片掉落/接住、灾难触发、建筑放置/摧毁、技能释放 | 事件驱动 | 可靠（有序） | TCP / UDP（可靠有序通道） | 高 |
| 阶段切换 | 游戏阶段变更（预告→碎片收集→建造→...） | 事件驱动 | 可靠（有序） | TCP / UDP（可靠有序通道） | 最高 |
| 天赋选择 | 天赋选择结果 | 事件驱动 | 可靠 | TCP | 中 |

### 3.2 高频状态同步详情

**同步内容（每50ms一次）：**

| 字段 | 类型 | 说明 |
|------|------|------|
| playerId | uint8 | 0=Aqua(水人), 1=Ignis(火人) |
| position | Vector2 | 角色世界坐标 |
| velocity | Vector2 | 角色速度向量 |
| animState | uint8 | 动画状态枚举（Idle/Run/Jump/Fall等） |
| facing | bool | 朝向（左/右） |
| timestamp | uint32 | 发送时间戳（ms），用于插值和延迟计算 |

> **设计说明**：高频状态使用不可靠UDP传输，允许丢包。接收端通过插值平滑处理，偶尔丢包不影响游戏体验。角色位置使用客户端预测+服务端校正（详见§五）。

### 3.3 中频状态同步详情

**同步内容（每100ms一次）：**

| 字段 | 类型 | 说明 |
|------|------|------|
| playerId | uint8 | 角色ID |
| hp | int16 | 当前生命值 |
| shelterEnergy | uint8 | 庇护能量值（0-100） |
| carriedFragments | uint8[] | 携带的碎片类型列表 |
| fragments[] | FragmentSync[] | 场上存活碎片的位置和类型 |

### 3.4 关键事件同步详情

**关键事件统一附带元数据：**

| 字段 | 类型 | 说明 |
|------|------|------|
| eventId | uint32 | 事件唯一ID（用于去重和顺序处理） |
| eventType | uint16 | 事件类型枚举 |
| playerId | uint8 | 发起玩家ID |
| timestamp | uint32 | 事件发生时间戳（ms） |
| payload | bytes | 事件特定数据（Protobuf序列化） |

## 四、关键事件同步策略

### 4.1 碎片系统同步

> **关联文档**：`碎片系统.md`、`章节策划文档_v2.0.md` §4.5 碎片掉落密度

| 事件 | 发起方 | 同步内容 | 处理方式 |
|------|--------|----------|----------|
| 碎片掉落 | **Host** | 碎片掉落计划（位置/类型/掉落时间/随机种子） | Host生成完整掉落计划，一次性同步给Client。双方各自模拟物理掉落轨迹 |
| 碎片接住 | 实际接住的玩家 | 碎片ID、玩家ID、接住时间戳 | 接住事件由实际接住的玩家发起，同步给对方 |
| 碎片消失 | 各端独立 | 无需同步 | 各端独立模拟3秒倒计时（轮次3为2.5秒），碎片自然消失 |

**碎片接住冲突处理：**

```
场景：两人同时接住同一碎片（触发×3奖励）
条件：两人接住事件的时间差 < 100ms
判定：Host判定为同时接住，触发×3碎片奖励
回滚：Client回滚本地状态，采纳Host判定结果
```

**碎片掉落计划同步流程：**

```
Host端:
  1. 阶段开始时，根据灾难类型和密度系数生成碎片掉落计划
  2. 将掉落计划（数组：{位置, 类型, 时间, 种子}）打包为Protobuf消息
  3. 通过可靠通道发送给Client
  4. 双方各自按计划执行物理掉落模拟

Client端:
  1. 接收掉落计划
  2. 本地模拟碎片物理掉落（与Host使用相同随机种子，确保轨迹一致）
  3. 碎片接住事件发送给Host
```

### 4.2 灾难系统同步

> **关联文档**：`灾难系统.md`、`灾难系统设计.md` §6.3 渐进入侵节奏

| 事件 | 发起方 | 同步内容 | 处理方式 |
|------|--------|----------|----------|
| 灾难开始 | **Host** | 灾难类型、参数（DPS/范围/持续时间）、随机种子 | Host在灾害冲击阶段开始时同步灾难类型和参数，双方各自模拟灾难效果 |
| 灾难强度变化 | 各端独立 | 无需实时同步 | 双方各自按时间轴计算渐进强度，不需实时同步（见下方时间轴） |
| 灾难结束 | **Host** | 灾难结束事件 | Host在灾害冲击阶段结束时同步，双方停止灾难效果模拟 |

**灾难渐进入侵节奏（双方独立计算，不同步）：**

| 时间段 | 强度 | 说明 |
|--------|------|------|
| 0-5秒 | 30% | 灾害开始，轻微影响 |
| 5-10秒 | 60% | 灾害加剧，建筑开始承压 |
| 10-15秒 | 100% | 灾害全盛，最大压力 |
| 15-20秒 | 80% | 灾害消退，但仍有压力 |

> 该时间轴为确定性计算（基于灾难开始时间戳），双方各自按时间轴推算当前强度，无需实时同步。

**随机性处理：**

```
Host端:
  1. 灾难开始时生成随机种子（uint32）
  2. 将种子随灾难参数一起同步给Client
  3. Host使用该种子初始化本地随机数生成器

Client端:
  1. 接收灾难参数和随机种子
  2. 使用相同种子初始化本地随机数生成器
  3. 双方随机序列一致，火焰龙卷路径、陨石落点等随机元素保持同步
```

> **设计说明**：种子同步确保双方灾难效果视觉一致，避免"我看到陨石砸这里，队友看到砸那里"的违和感。随机元素的实际伤害判定由Host权威执行。

### 4.3 建筑系统同步

> **关联文档**：`建造系统.md`、`地图设计.md`（15×8格建筑区域）

| 事件 | 发起方 | 同步内容 | 处理方式 |
|------|--------|----------|----------|
| 建筑放置 | 操作玩家 | 建筑类型、材料类型、网格位置 | 放置事件由操作玩家发起，同步给对方。双方各自创建建筑实例 |
| 建筑受损 | 各端独立 | 无需实时同步 | 双方各自计算建筑受伤（基于灾难DPS × 抗性等级 × 当前强度），不需实时同步 |
| 建筑修整同步 | **Host** | 所有建筑当前HP | 修整阶段开始时，Host同步所有建筑的当前HP，校正双方可能的偏差 |
| 建筑摧毁 | **Host** | 建筑ID、摧毁原因 | 摧毁事件由Host判定（建筑HP≤0时触发），同步给Client |

**建筑抗性等级参考（用于双方独立计算受伤）：**

| 等级 | 符号 | 伤害系数 | 说明 |
|------|------|----------|------|
| 免疫 | ★★★ | 0× | 完全免疫该环境伤害 |
| 强抗性 | ★★ | 0.3× | 受到30%伤害 |
| 抗性 | ★ | 0.6× | 受到60%伤害 |
| 无加成 | — | 1.0× | 正常伤害 |
| 弱点 | ✗ | 1.5× | 受到150%伤害 |

> **设计说明**：建筑受伤双方独立计算，修整阶段由Host校正。这是因为灾难强度为确定性时间轴函数，双方计算结果应一致，但浮点误差和丢包可能导致偏差，修整阶段校正可消除累积误差。

### 4.4 技能系统同步

> **关联文档**：`技能系统.md`、`技能系统设计.md`（3E+3Q卡牌选择）

| 事件 | 发起方 | 同步内容 | 处理方式 |
|------|--------|----------|----------|
| 技能释放 | 操作玩家 | 技能ID、目标位置、释放时间戳 | 释放事件由操作玩家发起，同步给对方 |
| 技能效果（视觉） | 各端独立 | 无需同步 | 双方各自模拟技能视觉效果（粒子、动画） |
| 技能效果（机制） | **Host** | 伤害/冻结等机制判定结果 | 伤害/冻结等机制效果由Host权威判定，同步结果给Client |

**技能释放同步流程：**

```
操作玩家端:
  1. 玩家按下技能释放键
  2. 本地立即播放技能视觉特效（减少延迟感）
  3. 发送技能释放事件（技能ID + 目标位置 + 时间戳）给对方
  4. 等待Host的机制判定结果

对方端:
  1. 接收技能释放事件
  2. 本地播放技能视觉特效
  3. 等待Host的机制判定结果

Host端（若Host非操作方）:
  1. 接收技能释放事件
  2. 执行机制判定（伤害计算、冻结判定等）
  3. 同步判定结果给双方
```

> **设计说明**：技能视觉效果立即本地播放（不等待网络确认），机制效果等待Host判定。这确保了视觉响应即时性，同时保证了机制判定的权威性。

## 五、延迟补偿机制

### 5.1 延迟补偿策略总览

| 机制 | 适用场景 | 说明 |
|------|----------|------|
| 客户端预测 | 本地角色移动 | 角色移动使用客户端预测，服务端校正。减少移动延迟感 |
| 插值 | 其他玩家角色位置 | 其他玩家角色位置使用插值平滑（100ms缓冲），避免瞬移 |
| 时间戳 | 关键事件 | 关键事件附带时间戳，接收方按时间戳顺序处理 |
| 冲突回滚 | 碎片接住冲突 | 碎片接住冲突时（两人同时接住同一碎片），以Host判定为准，Client回滚 |

### 5.2 客户端预测

```
本地角色移动:
  1. 玩家输入 → 本地立即应用移动（预测）
  2. 发送输入给Host
  3. Host执行权威移动计算
  4. Host返回权威位置
  5. Client对比预测位置与权威位置
     ├─ 误差 < 阈值 → 保持预测（无感校正）
     └─ 误差 ≥ 阈值 → 瞬移到权威位置（显式校正）
```

| 参数 | 建议值 | 说明 |
|------|--------|------|
| 校正阈值 | 0.5格 | 超过此误差才执行显式校正，避免频繁跳变 |
| 预测缓存 | 最近10帧 | 用于回滚和重放 |
| 最大预测距离 | 2格 | 超过此距离强制校正（防止预测发散） |

### 5.3 插值

```
远程玩家角色位置:
  1. 接收高频状态包（20Hz）
  2. 放入插值缓冲区（100ms = 2帧缓冲）
  3. 按时间戳排序
  4. 在两个最近的位置之间线性插值
  5. 渲染插值结果（平滑移动）
```

| 参数 | 建议值 | 说明 |
|------|--------|------|
| 插值缓冲 | 100ms | 约2个高频包的间隔 |
| 插值方法 | 线性插值 | 位置使用Vector2.Lerp |
| 外推限制 | 100ms | 超过缓冲区最新包时，最多外推100ms后停止 |
| 抖动消除 | 速度平滑 | 对插值后的速度做低通滤波，消除抖动 |

> **设计说明**：100ms插值缓冲引入约100ms的显示延迟，但对2D合作游戏而言完全可接受。优先保证视觉平滑性，避免角色瞬移。

### 5.4 时间戳与事件排序

```
关键事件处理:
  1. 发送方附带事件时间戳（毫秒级精度）
  2. 接收方将事件放入时间戳排序队列
  3. 按时间戳顺序依次处理事件
  4. 若收到过期事件（时间戳 < 已处理最新时间戳）:
     ├─ 幂等事件 → 忽略（已处理过）
     └─ 非幂等事件 → 回滚重放（如碎片接住冲突）
```

### 5.5 冲突回滚（碎片接住冲突）

```
碎片接住冲突处理流程:
  1. Host收到两个玩家的碎片接住事件
  2. 比较两个事件的时间戳
  3. 时间差 < 100ms → 判定为同时接住（×3奖励）
  4. 时间差 ≥ 100ms → 判定先到者接住
  5. Host发送判定结果给双方
  6. Client回滚本地状态，采纳Host判定
```

> ⚠️ **待验证**：100ms同时接住窗口是否合适，需原型测试调整。窗口过大可能导致"明显不同时"也被判定为同时。

## 六、断线重连状态恢复

> **关联文档**：`双生庇护系统设计.md` §6.5 断线/掉线处理机制

### 6.1 断线处理时间轴（设计已定稿）

| 阶段 | 时间 | 行为 | 网络层动作 |
|------|------|------|------------|
| 即时断线 | 0秒 | 游戏暂停，显示"队友已断开，等待重连..." | Host检测到Client心跳超时，触发断线流程 |
| 重连窗口 | 0-30秒 | 倒计时显示，游戏保持暂停 | Host保持房间状态，等待Client重连 |
| AI接管 | 30秒后 | AI接管掉线玩家 | Host启动AI逻辑控制掉线玩家角色 |
| 最终超时 | 120秒后 | 游戏结束，判定失败 | Host关闭房间，释放资源 |
| 重连成功 | 任意时刻 | 恢复玩家控制，无惩罚 | Host执行全量状态同步（见§6.2） |

### 6.2 重连全量状态同步

**重连成功后，Host向Client发送全量状态快照：**

| 恢复内容 | 同步字段 | 说明 |
|----------|----------|------|
| 角色状态 | HP、庇护能量值、位置、速度、携带碎片、动画状态 | 双方角色的完整状态 |
| 建筑状态 | 所有建筑的类型/材料/当前HP/网格位置 | 15×8格建筑区域内所有建筑 |
| 游戏阶段 | 当前游戏阶段（7阶段之一）、阶段剩余时间 | 确保Client恢复到正确的游戏阶段 |
| 碎片状态 | 当前存活碎片的位置和类型 | 场上所有未消失的碎片 |
| 天赋/技能 | 已选天赋列表、可用技能卡牌及冷却状态 | 全局天赋选择记录和技能状态 |
| 灾难状态 | 当前灾难类型、灾难强度、灾难随机种子 | 若处于灾害冲击阶段，需恢复灾难模拟 |
| 游戏进度 | 当前关卡（章/节/轮）、累计得分 | 全局游戏进度信息 |

### 6.3 重连同步消息结构

```protobuf
message ReconnectSnapshot {
  // 游戏进度
  int32 chapter = 1;          // 当前章节 (1-3)
  int32 section = 2;          // 当前节 (1-4)
  int32 round = 3;             // 当前轮 (1-3)
  GamePhase current_phase = 4; // 当前游戏阶段
  int32 phase_remaining_ms = 5; // 阶段剩余毫秒
  
  // 角色状态
  repeated PlayerState players = 6;  // 两个玩家的完整状态
  
  // 建筑状态
  repeated BuildingState buildings = 7;  // 所有建筑
  
  // 碎片状态
  repeated FragmentState fragments = 8;  // 场上存活碎片
  
  // 天赋/技能
  repeated TalentData talents = 9;        // 已选天赋列表
  repeated SkillState skills = 10;        // 技能状态（ID/冷却/可用次数）
  
  // 灾难状态（仅灾害冲击阶段）
  DisasterState disaster = 11;  // 当前灾难状态（可能为空）
  
  // 时间戳
  uint32 snapshot_timestamp = 12;  // 快照时间戳
}
```

> **设计说明**：全量状态同步使用可靠有序通道传输，确保Client恢复后状态与Host完全一致。同步完成后双方各自继续模拟。AI接管期间的任何状态变更已在Host的权威状态中体现，重连后直接同步即可。

### 6.4 AI接管期间的同步行为

AI接管期间（30秒后~120秒超时前），Host同时控制两个角色：

| 行为 | 说明 |
|------|------|
| AI角色移动 | Host本地模拟AI角色移动（跟随存活玩家、保持2格庇护距离） |
| AI角色高频状态 | Host正常发送AI角色的高频状态包给Client |
| AI角色不使用技能 | AI不触发技能释放事件（保守行为，避免误操作） |
| AI角色不捡碎片 | AI不触发碎片接住事件 |
| AI角色不建造 | AI不触发建筑放置事件 |
| AI角色受伤 | 双方各自计算（确定性时间轴），Host权威校正 |

> **关联设计**：AI接管行为规则详见 `双生庇护系统设计.md` §6.5。AI行为保守（不主动行动），避免因AI误操作导致游戏失败。

## 七、网络参数建议

### 7.1 核心参数

| 参数 | 建议值 | 说明 |
|------|--------|------|
| 服务器Tick Rate | 20Hz（50ms） | 高频状态同步频率 |
| 客户端插值缓冲 | 100ms | 其他玩家位置插值缓冲 |
| 超时判定 | 5秒无心跳判定断线 | 比游戏内30秒重连窗口更早检测 |
| 最大带宽预估 | < 50 KB/s | 2人+碎片+建筑状态，数据量小 |
| 协议 | UDP（可靠+不可靠混合） | 高频状态用不可靠，关键事件用可靠 |

### 7.2 超时与心跳机制

```
心跳检测:
  - Host和Client每1秒互发一次心跳包（不可靠UDP）
  - 连续5秒未收到对方心跳 → 判定断线
  - 断线判定后触发§六的断线处理流程

为什么5秒而非30秒:
  - 5秒检测确保快速感知断线
  - 30秒是"游戏内重连窗口"（允许玩家重新连接的宽限时间）
  - 检测断线（5秒）≠ 重连超时（30秒）≠ 最终超时（120秒）
```

| 时间节点 | 含义 | 触发动作 |
|----------|------|----------|
| 5秒 | 心跳超时，判定断线 | 游戏暂停，显示"队友已断开" |
| 30秒 | 重连窗口超时 | AI接管掉线玩家 |
| 120秒 | 最终超时 | 游戏结束，判定失败 |

### 7.3 带宽估算

| 同步类型 | 单包大小 | 频率 | 带宽占用 |
|----------|----------|------|----------|
| 高频状态（角色×2） | ~40 bytes | 20 Hz × 2人 | ~1.6 KB/s |
| 中频状态 | ~60 bytes | 10 Hz | ~0.6 KB/s |
| 关键事件 | ~100 bytes | 峰值~5次/秒 | ~0.5 KB/s |
| 心跳包 | ~10 bytes | 1 Hz × 2方向 | ~0.02 KB/s |
| **总计** | — | — | **~3 KB/s** |

> **带宽说明**：实测预估约3 KB/s，远低于50 KB/s上限。即使考虑碎片掉落高峰期（每轮20-35个碎片）和灾难特效同步，峰值带宽也不超过10 KB/s。
